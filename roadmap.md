# BLACK BUILDER Roadmap

## Done

- Color-coordinated agents and live connector wires.

- Decided on 7-agent architecture: PLANNER = cowork-style brain agent with high-reasoning model; SCAVENGER/BUILDER/STITCHER/FIXER/PUBLISHER/APP-WRAPPER = coders.
- Decided repo-per-function architecture (each agent/function owns its own repo).
- Confirmed APP-WRAPPER stays as a distinct agent rather than folding mobile output into the original six.
- Clarified build pipeline: SCAVENGER finds repos → BUILDER strips components → STITCHER assembles one repo → FIXER repairs → PUBLISHER deploys → APP-WRAPPER packages mobile.
- Prepared `HANDOFF.md` and centralized agent definitions in `src/lib/agents.ts`.
- Added `/privacy` and `/terms` pages with SEO meta and login-page footer links.
- Decided coding-agent engine for the six coder agents: Claude Agent SDK / Claude Code, run per-job in a throwaway sandbox (E2B or Daytona). Decided on desk research (setup cost, ops burden, fit for seven distinct agent roles) rather than a formal head-to-head spike against OpenHands — running that spike would have required standing up OpenHands' own backend/Docker-sandboxed control-plane just to confirm what the research already pointed to, which wasn't worth the infrastructure cost for this decision. `spike/stitcher-task/` remains available if OpenHands (or another engine) is worth re-evaluating later against real production data.
- Decided hosting/preview target for web outputs: Vercel. Both Vercel and Netlify are cost-equivalent here (free tier covers this), so the deciding factor was fit — Vercel's wildcard-subdomain/multi-tenant routing is more mature for this app's exact need (one auto-provisioned preview URL per generated app, on every run). Netlify's equivalent is newer and less proven for this pattern. Exact provisioning mechanism (API/DNS/cert automation) is still open — see `docs/agent-contracts.md`.
- Deployed `black-buillder` itself to Vercel (Production) via GitHub import, `NITRO_PRESET=vercel` env var overriding the Lovable config's Cloudflare default without touching the Lovable-managed `vite.config.ts`.
- ~~Decided PLANNER's model: Claude Opus 5.5 (`claude-opus-5-5`) at `effort: max`. Fable 5.1 was ruled out over its separate credit billing.~~ **Superseded** — see below: that "credit billing" concern was based on claude.ai's consumer-plan gating, which doesn't apply to API calls. On the API, Fable 5.1 is just another model at its own per-token rate; the real gate is a 30-day data-retention requirement, which this account already meets by default.
- Decided mobile target for APP WRAPPER: Capacitor, wrapping PUBLISHER's exact shipped web app. Signing-credential storage/provisioning remains a separate open question.
- Decided GitHub access model: a GitHub App (not OAuth App/PAT) with Contents R&W, Pull Requests R&W, org-level Administration (Write, for repo creation), and auto-included Metadata (Read). Code Search API is capped at 10 req/min regardless of auth — a constraint for SCAVENGER's search-retry budget.
- Decided per-agent model tiering: added a `coder_high` role to `llm-proxy` (defaults to `openai:gpt-6-astra`, deployed) for FIXER and APP WRAPPER specifically — they're the pipeline's two terminal correctness gates with no downstream re-check, so they get a stronger model than the other four coder-role agents (SCAVENGER stays `low_cost`; BUILDER/STITCHER/PUBLISHER stay `coder`).
- Re-picked the `low_cost` and `coder` role defaults for cheaper, competitive models: `low_cost` (SCAVENGER) now defaults to `dashscope:qwen3.5-flash` ($0.10/$0.40 per million, cheaper than the prior `gpt-6-luna` on output) instead of OpenAI; `coder` (BUILDER/STITCHER) now defaults to `dashscope:qwen3.8-max` ($2/$6, vs `gpt-6-sol`'s $2/$10 and well under `claude-sonnet-5`'s $2/$10) — same DashScope endpoint already wired in, model IDs and pricing verified against Alibaba's own docs. `qwen3-coder-plus` ($0.65/$3.25, coding-specialized) is a cheaper alternative for `coder` if we want to optimize further later.
- Added a `coder_max` role, PUBLISHER only, one tier above `coder_high`: `anthropic:claude-opus-5-5` @ `effort: max` — the exact same model+effort as PLANNER (via a separate role, so the two stay independently tunable). PUBLISHER, FIXER, and APP WRAPPER are the three stages called make-or-break for the whole app; PUBLISHER specifically was bumped to match PLANNER's tier, above FIXER/APP WRAPPER's `coder_high`. Also implemented `effort` for real in `llm-proxy` (`output_config.effort`, Anthropic-only) — it had been a documented decision for PLANNER since the first spec but was never actually sent on the request until now.
- Corrected the Claude entries in `llm-proxy`'s pricing table, which had been unverified placeholders: `claude-opus-5-5` is $4/$20 per million (was listed as $6/$30), `claude-sonnet-5` is $2/$10 (was $3/$15), `claude-fable-5-1` is $10/$50 (was $15/$75), and `claude-haiku-4-5` is $1/$5 (was listed under a stale date-suffixed id `claude-haiku-4-5-20251001` — Anthropic model ids never carry a date suffix). Verified against Anthropic's own current pricing.
- Moved `planner`, `coder_high`, and `coder_max` to `claude-fable-5-1` (all four agents: PLANNER, FIXER, PUBLISHER, APP WRAPPER). Same per-token price as the prior `coder_high` pick `gpt-6-astra` ($10/$50), but ahead of it on the Coding Agent Index (70 vs 67) — a same-cost upgrade for FIXER/APP WRAPPER. For PLANNER/PUBLISHER it's a real cost increase over the prior `claude-opus-5-5` pick (2.5x per token: $4/$20 → $10/$50), accepted given confirmed budget headroom (see the Lovable-vs-Completer-App cost comparison) and Fable 5.1's benchmark lead. `coder` (BUILDER/STITCHER) stays on `qwen3.8-max` — Opus 5.5 was checked against it directly and only led clearly on broad coding benchmarks, not on SWE-bench Pro (real-repo resolution, the closer analog to BUILDER/STITCHER's actual job), so the swap wasn't worth it there.
- Split `llm-proxy`'s 5 shared tier-based roles (`coder`, `coder_high`, `coder_max`, `low_cost`) into 7 — one per agent (`scavenger`, `builder`, `stitcher`, `fixer`, `publisher`, `wrapper`, plus the existing `planner`). Named `wrapper` (not `app_wrapper`) specifically to match the database's existing `agent_type` enum (`run_stages.agent` was already `wrapper`) — caught this mismatch before it shipped further. Model defaults unchanged; the point is that BUILDER and STITCHER (previously forced to share `coder`) and FIXER and APP WRAPPER (previously forced to share `coder_high`) can now be independently retuned. Also made `effort` env-overridable per role (`LLM_ROLE_*_EFFORT`, matching the existing `LLM_ROLE_*` model override) — previously hardcoded, code-change-only. Rationale: a private/self-hosted buyer paying a premium one-time price should get real per-agent control over both model and effort, not just the shared-tier defaults hosted/consumer users get.
- Built PLANNER for real: a new `planner` Edge Function that reads `runs.prompt`/`input_repo_url`, calls `llm-proxy` (role `planner`) to produce a locked spec (function_keys, descriptions, acceptance signals, out-of-scope notes, or an escalation signal for ambiguous/contradictory prompts), validates the response structurally, stores it as an `artifacts` row (`kind="spec"`) in a new private Storage bucket (`artifacts`), and reports progress via `runner-callback`. `start-run` now invokes it automatically (fire-and-forget) right after creating a run's rows. Brought the three pre-existing pipeline functions (`start-run`, `cancel-run`, `runner-callback`, built by an earlier session directly against Supabase, never committed to this repo) into version control in the same pass, and extended `runner-callback`'s `logs` field to accept per-line severity (`info`/`warn`/`error`) — it previously hardcoded every log line to `info`, which would have silently broken the shared logging convention in `docs/agent-contracts.md` for every agent, not just PLANNER.
- Verification: unit-tested PLANNER's JSON-extraction and spec-validation logic directly (10 cases — clean JSON, fenced JSON, escalation, missing escalation reason, duplicate function_key, empty functions array, malformed input, missing required field — all pass). Could not run a true end-to-end live test: this sandbox's network policy blocks direct HTTPS to `*.supabase.co`, and the service-role key needed to call the function's own auth-gated endpoint was never available in this session by design (kept out of chat/logs). Real end-to-end verification still needs either a run triggered through the actual app once the frontend is wired to `start-run`, or the user invoking it directly with real credentials.
- Bumped FIXER's default effort to `max` (was the Fable 5.1 default `high`), matching PLANNER/PUBLISHER. FIXER is the last stage that actually judges code correctness — nothing downstream re-checks its output, so a missed bug ships silently, which is a worse failure mode than PUBLISHER's more binary/verifiable deploy-succeeded-or-didn't job. APP WRAPPER stays at the `high` default (mobile-only blast radius if it misses something). Considered and ruled out "ultracode" as a higher tier — verified it's a Claude Code product feature (session-scoped, sends `xhigh` + enables subagent orchestration), not an Anthropic API `output_config.effort` value; `max` is the real ceiling for what `llm-proxy` actually calls (the raw Messages API, not through Claude Code).
- Fixed a real gap found while wiring SCAVENGER in: `runner-callback` updated `runs.current_stage` on pass/fail but never actually invoked the next stage — PLANNER passing did nothing beyond PLANNER. It's now the actual pipeline runner per `docs/agent-contracts.md`'s shared conventions: fire-and-forget invokes the next agent's Edge Function on `passed` (same pattern as `start-run` → PLANNER), sets `runs.status="passed"` + `finished_at` when APP WRAPPER (the last stage) passes, sets `status="failed"` + `finished_at` on any `failed`, and flips `runs.status` off `"pending"` to `"running"` on the first `running`/`escalated` callback of a run.
- Built SCAVENGER for real: a new `scavenger` Edge Function that reads PLANNER's spec artifact, searches GitHub Code Search per function_key (deterministic keyword-based queries, throttled to stay under GitHub's flat 10 req/min code-search cap), fetches license + pinned commit SHA for candidate repos, and uses one batched LLM call (role `scavenger`) to judge functional fit among the license-acceptable candidates. Records every candidate considered as a `sources` row (accepted or rejected, with a reason), falls back to `source_type="scratch"` when nothing matches, and escalates the whole run if a function_key's only candidates are license-incompatible rather than silently downgrading. Decided the previously-undocumented license allow-list (permissive OSS only — MIT/Apache-2.0/BSD-2/BSD-3/ISC/0BSD/Unlicense/CC0-1.0) as part of this build; see `docs/agent-contracts.md`. Requires a new `GITHUB_TOKEN` Supabase secret (not yet confirmed set — SCAVENGER escalates cleanly with a clear message if it's missing rather than guessing).
- Added `runs.output_repo_url` (migration `add_runs_output_repo_url`) — the target repo BUILDER will create/write the generated app into and PUBLISHER will open a PR against. Null until BUILDER creates it on first use. This was a real schema gap: nothing recorded where a run's generated code actually lives, which would have blocked BUILDER/PUBLISHER regardless of how the sandbox-engine question below gets resolved.

- **Discovered and did not build around a real architecture blocker:** BUILDER, STITCHER, and FIXER's contracts require actually cloning/extracting code, installing dependencies, and running builds/tests — none of which a Supabase Edge Function can do (stateless Deno isolate, no subprocess or persistent filesystem). This isn't a missing secret, it's the sandboxed coding-agent runtime (Claude Agent SDK / Claude Code in a throwaway E2B or Daytona sandbox) already decided above but never actually stood up as infrastructure. APP WRAPPER has the same gap plus needs a native Android SDK/Gradle toolchain on top. PUBLISHER is blocked too, for a second reason: it needs FIXER's branch to exist, and its own deploy mechanism (Vercel wildcard-subdomain provisioning) is separately still undecided. Rather than ship fake/non-compliant stand-ins for these five agents (which would silently abandon the locked sandbox-engine decision and couldn't actually satisfy their build/test/deploy success criteria), stopped here and flagged it for a decision — see `docs/agent-contracts.md`'s Open dependencies. **Superseded below** — the sandbox question is now resolved and BUILDER is built.
- **Resolved the sandbox-engine blocker: E2B, driven directly rather than through its turnkey Claude Code template.** Confirmed `npm:e2b` imports cleanly under Supabase's Deno edge runtime (deployed a scratch test function before committing to the approach). Then hit the real fork in the road: E2B's ready-made `claude` sandbox template only talks to Anthropic's API, but BUILDER/STITCHER were deliberately put on Qwen3.8-Max for cost/benchmark reasons — using the turnkey template would have silently overridden that decision. Put it to the CEO directly rather than picking silently: (A) switch BUILDER/STITCHER to an Anthropic model for a simpler build, or (B) keep Qwen3.8-Max and drive a bare E2B sandbox with a custom tool-use loop through `llm-proxy` instead. **Decided: B** — no reason to give up the cost optimization to save build time on my end.
- Built BUILDER for real: a new `builder` Edge Function implementing option B above. Creates the run's output GitHub repo on first use (private, under a new write-scoped `GITHUB_WRITE_TOKEN` secret — SCAVENGER's `GITHUB_TOKEN` stays read-only/least-privilege and is reused only for cloning source repos), seeding it from `runs.input_repo_url` when set. Spins up a bare E2B sandbox per run for git/filesystem work; for each spec function_key, clones the accepted source (if any) into the sandbox, builds an LLM context from its file listing/contents, and calls `llm-proxy` (role `builder`, still Qwen3.8-Max) to decide exactly what to write under `functions/<function_key>/` — validated so the model literally cannot write outside that folder. Escalates if the model itself flags a source as fundamentally wrong for its function (a safety net catching cases SCAVENGER's shallower judgment missed) rather than forcing a bad fit. Commits and pushes to `run/<run_id>`, records the notices artifact (license attribution + the per-function_key extracted-path map STITCHER needs, both in one artifact). Fixed a second real gap surfaced by this: `runner-callback` never had a way to record which branch a stage worked on at all (`run_stages.branch` was always null) — added a `branch` field to the callback payload.
- Verification: unit-tested BUILDER's pure logic (`parseOwnerRepo`, the builder-response validator including the path-prefix safety check — 12 cases) directly, all pass. Confirmed the full function (including the `npm:e2b` import) deploys successfully under Supabase's Deno runtime. Same live end-to-end limitation as every prior agent (sandbox network policy blocks `*.supabase.co`, no service-role key in this session) — additionally needs `E2B_API_KEY` (confirmed set) and `GITHUB_WRITE_TOKEN` (not yet confirmed set) before a real run can exercise it.
- **Re-examined the STITCHER/FIXER/PUBLISHER blockers now that BUILDER proves the E2B pattern works:** STITCHER and FIXER are no longer architecturally blocked — a bare E2B sandbox can run real `npm install`/build/test commands exactly as well as it ran BUILDER's git operations, they just haven't been built yet. PUBLISHER's PR-opening half doesn't need a sandbox at all (FIXER's sandbox will have already pushed the final commits) — only its Vercel deploy half is still blocked, on the wildcard-subdomain provisioning decision, unchanged. APP WRAPPER remains genuinely blocked: it needs a *custom* E2B template with an Android SDK/JDK/Gradle toolchain (E2B's default template doesn't have one — solvable, just not done) plus the still-undecided signing-credential provisioning. See `docs/agent-contracts.md`'s Open dependencies for the per-agent breakdown.
- Built STITCHER for real: a new `stitcher` Edge Function. Since BUILDER already writes every function into one shared output repo, STITCHER's job narrowed to turning independent `functions/<function_key>/` folders into one coherent, installable project rather than merging separate repos. Clones BUILDER's output repo at the same `run/<run_id>` branch (no new branch), deterministically discovers which npm packages are actually imported via `grep` across `functions/` (not LLM-guessed — kept the LLM out of a job a shell command does reliably), then one `llm-proxy` call (role `stitcher`, still Qwen3.8-Max) produces a root `package.json` + minimal entry point tying the functions together. The LLM is barred from writing anything inside `functions/*/` at all (validated, same pattern as BUILDER's function-folder restriction). Then does something no earlier agent could do: actually runs `npm install` in the sandbox and checks the real exit code — on failure, feeds the actual npm error back to the LLM for one fix-up retry (a genuinely stronger correction signal than guessing blind) before giving up. Records the manifest artifact: entry point, resolved dependencies, and a path→function_key map built deterministically from BUILDER's own notices artifact rather than re-derived by an LLM.
- Verification: unit-tested STITCHER's pure logic (`normalizePackageName`, `extractPackageNames`, the merge-response validator including the functions/-write-guard) — 13 cases, all pass. Confirmed the function deploys successfully. Same live end-to-end limitation as every prior agent (sandbox network policy, no service-role key) — this one is closer to real end-to-end verification than any prior agent once a live run reaches it, since `npm install` succeeding or failing is checked for real, not asserted.
